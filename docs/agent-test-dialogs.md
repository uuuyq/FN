# FNote Agent 手动测试对话手册

测试日期：2026-11-16。基于当前 Agent 注册的 12 个工具与会话机制编写。

用法：每个会话按顺序发送代码块中的用户输入（点击代码块右上角复制按钮即可整条复制），观察 Agent 回复、工具调用与确认卡片行为。标注【卡片】的步骤会出现确认卡片，需要手动点击"确认"或"取消"。

---

## 会话 1：训练记录 - 基础新增（覆盖核心写入路径）

**测试目标**：save_workout 新增、确认卡片展示、确认后落库。

**第 1 步**（出现新增训练卡片【确认】）

```
今天练胸，杠铃卧推 60kg 做了 5 组，每组 8 次
```

预期：卡片摘要含今天日期、卧推 60kg 5×8；确认后回复简短成功，回执含记录 ID。

**第 2 步**（点击确认）

预期：训练日历/列表出现该记录；Agent 续跑回复确认结果。

**第 3 步**（出现修改卡片【确认】）

```
刚才那组最后一组其实只做了 7 次
```

预期：Agent 读取记录后给出修改卡片，before/after 对比可见第 5 组 8→7。

**第 4 步**（点击确认）

预期：记录版本 +1，内容更新。

**检查点**：卡片摘要格式（日期+动作+组次）、确认后续跑消息、修改卡片包含 before/after。

## 会话 2：训练记录 - 信息缺失与追问

**测试目标**：missing_key_information、集中追问、不重复询问、allow_missing 跳过。

**第 1 步**

```
今天练了卧推，挺累的
```

预期：无卡片，Agent 集中追问次数/重量等关键信息，不逐条追问。

**第 2 步**（出现卡片【确认】）

```
重量 60 公斤，次数没数，别问了
```

预期：卡片 allow_missing 含 reps，披露缺失字段。

**第 3 步**（点击确认）

预期：记录保存，次数为空（非 0）。

**第 4 步**（出现卡片【确认】）

```
深蹲做了 5 组每组 8 次，重量没记
```

预期：卡片 weight_kg 为 null；确认后重量为空。

**第 5 步**

```
卧推 60 公斤 5 组 8 次，我不确定是单边还是总重
```

预期：无卡片，Agent 澄清单边/总重口径后再提案。

**检查点**：追问一次问全、缺失字段在卡片可见、0 与 null 的区分。

## 会话 3：训练记录 - 日期、时间与组类型

**测试目标**：相对日期、时间解析、热身组、连续相同组聚合。

**第 2 步**（点击确认）

预期：落库日期正确。

**第 3 步**（出现卡片【确认】）

```

```

预期：热身组 kind=warmup，正式组正常；卡片摘要区分热身/正式。

**第 4 步**（点击确认）

预期：记录含热身组与正式组。

**第 5 步**（出现卡片【确认】）

```

```

预期：日期解析为上周三；组次数分别记录（10、10、6）。

**检查点**：相对日期按用户时区、actual_time、warmup 组不强制次数。

## 会话 7：训练记录 - 删除与撤销

**测试目标**：delete_workout、undo_operation、撤销限制。

**前置**：先记录一条训练并确认。

**第 1 步**（出现删除卡片【确认】）

```
把今天那条卧推记录删掉
```

预期：卡片显示目标日期与动作数。

**第 2 步**（点击确认）

预期：记录软删除，日历中消失。

**第 3 步**（出现 undo 卡片【确认】）

```
我后悔了，撤销刚才的删除
```

预期：Agent 调 list_operations 找到操作，给出撤销卡片。

**第 4 步**（点击确认）

预期：记录恢复，内容与删除前一致，版本递增。

**第 5 步**

```
再撤销一次刚才那个撤销
```

预期：提示撤销操作本身不可再撤销。

**第 6 步**

```
我最近七天做过哪些训练操作
```

预期：list_operations 列出操作与可撤销状态。

**检查点**：撤销恢复快照保留组 ID；已撤销操作 can_undo=false。

## 会话 8：撤销 - 版本冲突场景

**测试目标**：撤销目标已被修改时的 version_conflict。

**前置**：记录一条训练并确认；再让 Agent 修改该训练（如卧推改 65kg）并确认。

**第 1 步**（在页面上手动编辑该记录任意字段，使版本变化）

**第 2 步**

```
撤销刚才 Agent 做的那个修改
```

预期：撤销校验失败（version_conflict），卡片冲突状态，续跑回复解释原因。

**检查点**：冲突后卡片状态为 conflict。

## 会话 19：并发与轮次机制

**测试目标**：conversation_busy、重试、全局容量。

**第 1 步**：发送一条消息，在 Agent 回复过程中立即再发一条。

预期：第二条被拒（conversation_busy）或前端禁用。

**第 2 步**：断开模型网络后发送消息。

预期：轮次失败，显示错误。

**第 3 步**：恢复网络，点击重试。

预期：轮次重跑，保留原用户消息。

**第 4 步**：失败后先发新消息，再对旧轮次点重试。

预期：旧轮次重试被拒（turn_not_retryable，已有更新的用户消息）。

**第 5 步**：待确认卡片存在时，Agent 正在处理新消息，点击旧卡片确认。

预期：确认被暂停（conversation_busy），处理完成后可确认。

**检查点**：失败错误码展示（model_timeout/model_failed 等）；重试语义。

## 会话 20：会话管理

**测试目标**：会话创建/重命名/删除、跨会话隔离。

**第 1 步**：新建会话 A，记录一条训练并确认。

**第 2 步**：新建会话 B，发送：

```
我最近一次训练是什么
```

预期：能查到（数据按用户隔离，会话只是对话容器）。

**第 3 步**：重命名会话 B。

预期：标题更新。

**第 4 步**：在会话 A 有 pending 卡片时删除会话 A。

预期：卡片被取消（cancelled），会话删除。

**第 5 步**：删除正在运行轮次的会话。

预期：被拒（conversation_busy）或先等待完成。

**检查点**：删除会话时 pending 卡片状态变为 cancelled。
