# Agent 端到端测试说明

日期：2026-11-10。当前脚本按已确认的后端方案及前端适配契约编写；前端更新后已执行验证，结果见文末。

## 测试边界

使用真实浏览器、生产前端构建、真实 FastAPI、认证 Cookie、SSE、业务工具、确认接口和 SQLite。仅替换外部模型 Provider，返回确定性的原生工具调用和回复。API 读取用于校验实际数据；冲突、隔离和幂等场景通过 API 制造或重放条件，主流程由 UI 驱动。

不使用用户运行数据库或外部 AI 密钥；每个脚本创建独立数据库和测试账号。扩展脚本使用动态空闲端口。截图、trace、服务器日志及临时库保存在 runtime 下，便于失败定位。测试桩仅由 tests.tooling.e2e_app 显式启动，不能在正式服务中启用。

这组脚本验证产品和 Agent 执行流程，不验证真实模型的中文理解能力。上下文超限、模型超时的浏览器场景使用 Provider 错误注入验证 UI；真实时间预算、归档校验、事务回滚等仍由后端回归测试验证。循环上限场景则实际连续调用查询工具直到触发预算。

## 核心流程：calendar-flow.mjs（9 组）

| 组 | 覆盖内容 |
| --- | --- |
| 1 | 新增卡片出现前后均未写入；纠正内容使旧卡片失效；刷新恢复卡片；确认保存一次；重复确认不重复新增 |
| 2 | 查询结果回传模型并显示答案；隐藏工具 JSON 和空助手气泡；取消新增无写入；普通查询也使旧卡片失效 |
| 3 | 查询列表 → 详情 → 修改工具；修改前后展示；确认前版本不变；确认后保留记录、动作及组 ID |
| 4 | 卡片生成后由 API 修改记录；确认返回 conflict，界面显示数据变化，不能覆盖新值 |
| 5 | 取消删除保留数据；确认删除后列表与详情不可见 |
| 6 | 信息不足时追问；用户允许重量和次数留空仍需卡片确认；null 不变成零；自定义动作确认前不存在、确认后只创建一次 |
| 7 | 个人条件、动作偏好、器械统一按钮确认；实际业务数据更新；确认不额外创建模型轮次 |
| 8 | 模型失败后用户显式重试；不重复保存用户消息 |
| 9 | 刷新后全部历史卡片保持终态；无残留确认按钮和浏览器运行异常 |

## 异常与历史：agent-resilience.mjs（12 组）

| 组 | 覆盖内容 |
| --- | --- |
| 1 | pending 卡片刷新恢复，ID 不变且只显示一次 |
| 2 | 新消息使旧卡片失效；旧确认 API 返回 409，不发生写入 |
| 3 | 双击确认仅写一条训练、产生一条执行事件，不新增模型轮次 |
| 4 | 服务端提交后丢弃确认响应；前端恢复终态；原请求 ID 重放不重复写入 |
| 5 | 慢速轮次运行时刷新页面，再从历史打开；恢复原轮次，仅有一条用户输入及一个轮次 |
| 6 | context_too_large 提示新建会话，无写入或卡片，不提供无意义重试 |
| 7 | model_timeout 显示超时提示，无写入或卡片 |
| 8 | 实际查询工具循环触发 agent_loop_limit，显示达到上限，无业务写入 |
| 9 | 第二个真实登录账号不能读取第一人的会话、轮次或确认其操作；训练与会话列表隔离 |
| 10 | UI 重命名及删除会话；删除会话后保存过的训练仍在 |
| 11 | 43 条用户输入及完整工具历史发送模型；序号不重复；刷新后最早与最新消息均可见 |
| 12 | 缺 CSRF 的确认被拒绝；同请求 ID 携带不同参数返回 409，无额外写入 |

共 21 组场景。部分场景是同一工作流的连续检查，不等同于 21 个完全独立的 Playwright Test 用例。核心脚本共享一个会话按顺序走完生命周期；异常脚本按组新建会话，保持同一用户及测试数据库，需要训练数据的分组复用该脚本前面已保存的记录。核心脚本遇错停止；异常脚本记录各分组失败截图后继续，最后汇总失败并以非零状态退出。

## 文件与运行方式

- tests/tooling/e2e_app.py：确定性模型桩，按当前用户轮次推进工具调用，正确解包工具结果的 data，避免旧轮工具结果干扰新轮。
- tests/tooling/e2e_setup.py：导入动作目录，创建 e2e-user 与 e2e-other。
- tests/browser/calendar-flow.mjs：核心完整工作流。
- tests/browser/e2e-harness.mjs：扩展测试的数据库、服务、浏览器、trace 和清理流程。
- tests/browser/agent-resilience.mjs：异常、历史与隔离。

前端完成后，在 frontend 目录执行：

```powershell
pnpm build
pnpm test:e2e                 # 依次运行两套脚本
pnpm test:e2e:core            # 仅核心流程
pnpm test:e2e:resilience      # 仅异常与历史
```

使用已有 Python 环境，默认 backend/.venv/Scripts/python.exe，可通过 PYTHON 指定。浏览器默认使用已安装 Chrome，其他 Chromium 可通过 BROWSER_EXECUTABLE 指定。无需运行开发服务器；测试服务从 frontend/dist 提供构建产物。

如果本机 pnpm 包装命令触发依赖重装，可直接使用现有依赖构建和运行：

```powershell
# frontend 目录
node node_modules/typescript/bin/tsc --noEmit
node node_modules/vite/bin/vite.js build
node ../tests/browser/calendar-flow.mjs
node ../tests/browser/agent-resilience.mjs
```

首次验证的唯一产品失败为 context_too_large 场景：前端正确显示上下文过长及新建会话提示，但仍显示“重试本轮”。frontend/src/conversation-types.ts 的 canRetry 未排除上下文超限。

异常测试产物为 `runtime/agent-resilience-6PQcBt/`，包含场景截图、页面文本、trace-0.zip 和 server.log。此轮其余场景均通过，包括 43 条用户输入的完整历史及刷新恢复。

验证过程中修正了测试自身的等待时序：send 在 SSE 完成后，还要等待前端处理完历史刷新和输入清空再发送下一条；并将等待响应与点击组合处理，避免未处理的 Promise 拒绝使进程直接退出。异常测试现在会汇总全部分组结果。

本轮使用本地 tsc、Vite 和 Node 直接执行，未访问真实模型；测试数据库独立于用户数据库。
